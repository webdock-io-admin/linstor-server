Title: 9.3.4: attach of a local disk to a resource in use by a diskless Primary hangs (drbdsetup attach and udev probe-bcache in D state); a second resource's receivers deadlock in conn_disconnect / drbd_suspend_io

## Environment

- DRBD kernel module 9.3.4 (api:2/proto:118-125), GIT-hash e59b287b199f7224468af85b68a10e83c68213f5, drbd-dkms 9.3.4-1ppa1~noble1 from ppa:linbit/linbit-drbd9-stack
- drbd-utils 9.35.0-1ppa1~noble1
- Kernel 7.2.11-zabbly+, Ubuntu 24.04, ZFS zvols as backing devices
- LINSTOR 1.35.2 drives the configuration. Resource options: protocol C, `quorum majority`, `on-no-quorum suspend-io`, `ping-int 3`, `connect-int 3`, `c-min-rate 250M`, two paths per connection.
- udev: `bcache-tools` (Ubuntu 24.04) installs `69-bcache.rules`, which does not exclude `drbd*`, so `/usr/lib/udev/probe-bcache` reads the first sectors of every new drbd minor.

## Topology

Node C was a compute node running VMs as a **diskless Primary**. Nodes A and B are the diskful storage pair. LINSTOR's `toggle-disk` added a local diskful replica on C to resources that were in use by running VMs.

R9 is a different resource from R8 (also in use on C). Its two receivers serve two different connections. One sits in `conn_disconnect` waiting for a mutex held by the other, which waits in `drbd_suspend_io` for I/O to drain. R9's connections at that time: A `Timeout`, another compute node `NetworkFailure`, B `SyncTarget` (23:47:40). We cannot tell from these lines whether R9's hang depends on R8's attach or only coincides with it. Both happened on the same node within four minutes.

### Peer view (node A, captured 00:01-00:06 before any recovery; node B saw the same)

- R8: A UpToDate; peer C `Connected` but `WFBitMapS` since 23:44:03 (vol0) and 23:45:31 (vol1); peer disk Inconsistent; out-of-sync 9.6 GiB / 88 MiB; the bitmap never arrives.
- R9: A's disk `Outdated` on both volumes; C `Connecting`/`Off` since 23:47, with a remote state-change attempt from C every 60 s (11 by 00:06).

### Consequences

LINSTOR's satellite on C timed out on every `drbdadm` call from 23:47:50 ("The external command 'drbdadm' did not complete within the timeout (45 s)"). The controller reported "No response generated by handler" for that node about 50 times in the following hour. Recovery needed a host reboot of C, and the shutdown itself hung for about an hour on the D-state tasks before systemd forced it.

## Questions

1. Is attaching a local disk to a resource whose device is in use by a (diskless) Primary on the same node expected to be safe? Here `drbdsetup attach` blocked in `drbd_nl_attach_doit` while reads from udev's `probe-bcache` on the same minor sat in `__drbd_make_request`.
2. Should udev probing of drbd minors be avoided, or tolerated, during attach? We will add a udev rule that excludes `drbd*` from `69-bcache.rules` either way, but other probers (blkid, multipath) open new minors too.
3. Is the R9 lock-up (one receiver in `conn_disconnect` waiting for a mutex held by another receiver in `drbd_suspend_io` from `receive_sizes`) a known pattern? Could the second receiver wait for I/O that cannot drain while the connection is being torn down?
