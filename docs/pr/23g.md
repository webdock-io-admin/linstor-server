# Fix 23g: retry a busy `zfs destroy` for a time, not a count

Base: fix 23b (branch fix/linstor-server-23-hold-backing-devices, 8cc324044). Replaces the budget of fix 1 (eb2e9e420).

## Problem
`zfs destroy` right after `drbdsetup down` fails with `dataset is busy` while the zvol is still open. Fix 1 retries this 6 times at 200, 400, 800, 1600, 2000, 2000 ms, so about 7 s of sleep.

Under write load that is not enough. One delete on our dev cluster (2026-11-06, loaded leg):
- The detach's last close of the zvol ran for 6.0 s in a kworker, after the DRBD minor was already gone. Most of that is a txg sync (`zvol_last_close` → `txg_wait_synced`).
- The destroy failed 6 times with "busy", and the 7th attempt succeeded at about +7 s.

So the retry budget covered it by about 1 s. Loaded txg waits on the same cluster reach 7.0 s.

## Cause
`ZfsCommands.destroyRetryHandler()` (satellite/.../zfs/utils/ZfsCommands.java:129-142 before this fix) bounds the retries by count. `Commands.genericExecutor` (server/.../storage/utils/Commands.java:93) re-runs the command for as long as the handler says so. A count bound turns into a time bound that is just as long as the backoff sums up to, regardless of how long the zvol actually stays open.

Waiting "until the DRBD minor is gone" is not a fix: the minor is gone before the first busy, and the close that keeps the zvol busy runs after it.

## Fix
- `RetryIfDeviceBusy.withDeadline(deadline, initial, max[, sleeper, clock])` retries a busy command until `deadline` ms have passed since the first busy failure.
  - The time is measured on a monotonic clock (`System.nanoTime`) and includes the commands' own run time.
  - The delays still double up to `max`. The last sleep is cut so that it ends at the deadline.
  - It still stops at once on any error whose stderr has no "busy".
  - A non-positive deadline is rejected.
  - The existing constructors and their count-based behaviour are unchanged (LVM and SPDK callers).
- ZFS destroy uses it with deadline 20 s (≈ 3× the 7.0 s loaded maximum), initial 200 ms, max 2 s: 200, 400, 800, 1600, then 2000 ms. A destroy that stays busy fails as before, after about 20 s plus the run time of its last attempt: at most 14 attempts, fewer when the attempts themselves take time.
- From review, for all callers: an interrupt during the sleep now ends the retries and keeps the thread's interrupt flag. Before, it was swallowed and the command ran again.
- Cost: the DeviceManager run is sequential, so a destroy that stays busy blocks the run for up to 20 s instead of ~7 s before failing.

## Tests
- `RetryIfDeviceBusyTest` (9): the 4 existing cases, plus an interrupt case, a non-positive-deadline case and 3 new ones on a fake clock:
  - the deadline bounds the total wait, not the count;
  - the command's run time counts against the deadline;
  - a non-busy error stops the retries.
- `ZfsCommandsDestroyRetryTest` (3):
  - busy 7 times, then OK, succeeds on the 8th attempt (fix 1 failed here);
  - always busy, on a fake clock where the commands take no time: sleeps 200, 400, 800, 1600, 2000 × 8, 1000 (sum 20,000 ms), then a StorageException;
  - a non-busy error is not retried.
- Mutation check: with the deadline set to 7 s, both new destroy tests fail.
