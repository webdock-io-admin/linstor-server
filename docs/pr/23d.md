# Fix 23d: create the clone base snapshot and its two marks in one `zfs snapshot`

Base: fix 23b (5f67bb10e, docs up to 8cc324044) on the v3-r2 set (v1.35.3 + fix 16 + #545 + fix 20) + fixes 21, 22.

## Problem
`ZfsProvider.createSnapshotForCloneImpl()` (1.35.3 ZfsProvider.java:984-1010) runs three commands per source volume:
- `zfs snapshot <pool>/<src>@<CF_…>`;
- `zfs set linstor:clone_for=<clone>`;
- `zfs set linstor:marked_for_deletion=true` on that snapshot.

Each is its own ZFS sync task, which waits for a txg sync under load: 6 waits per 2-volume clone per storage node.

A failure or satellite crash after the snapshot but before the sets leaves a CF_ snapshot without the marks. The cleanup never removes it, and a retry reuses it through infoListCache unmarked.

The exec sequence of one clone on our dev cluster (idle, 2026-11-06) shows exactly these 3 commands per volume on the source.

## Fix
- `ZfsCommands.userPropOption(name, value)` returns `-o linstor:<name>=<value>`.
- The clone base snapshot is created with `zfs snapshot -o linstor:clone_for=<clone> -o linstor:marked_for_deletion=true …`. `createSnapshotFullName` already passes extra arguments before the snapshot name.
- The on-disk result is identical: the same two local user properties. It is one sync task, and the marks are atomic with the snapshot. There is no feature flag. `markForDeletion()` is still used by the rename/delete path.
