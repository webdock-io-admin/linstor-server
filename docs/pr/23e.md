# Fix 23e: list only the ZFS datasets a device manager run needs (opt-in)

Base: fix 23d (e38ce9ad3).

## Problem
Every device manager run's prepare step (AbsStorageProvider.prepare → updateVolumeAndSnapshotStates → ZfsProvider.getInfoListImpl → ZfsUtils.getZfsList) runs:
- `zfs list -r -t volume,snapshot` on each volume dataset;
- `zfs get -r -s local linstor:marked_for_deletion` on the same.

`-r` returns every snapshot of the volume. On a clone source with 1,914 snapshots (zfs clones pin their origin snapshots) each call takes ~0.78 s.

A clone is three controller steps on the source, each one device manager run: suspend-io, CF_ snapshot, resume-io. Two of those runs' prepares fall inside the suspend. Measured on our dev cluster, idle, 2026-11-06: suspend-io 4.1 s, of which 3.1 s were the four walks and 0.25 s the snapshots. For a VM used as a clone source this is a guest I/O stall that grows with its clone count.

## Change (only with `LINSTOR_SATELLITE_ZFS_TARGETED_LIST=true`)
- `getInfoListImpl` lists names, without `-r`:
  - the volume datasets;
  - LINSTOR's snapshot objects (with and without the rename suffix, as snapshotExists looks them up);
  - the CF_ clone-base snapshot names of the resource's pending clone properties;
  - in a second targeted call, the origin snapshots of the listed volumes.
- `zfs get` reads the property from the same names, without `-r`.
- `ZfsInfo.snapshotsComplete` is true only for volumes listed with `-r`.
  - `delete()` and the deletion cascade reload a volume recursively before `canDelete()`, the only reader of `ZfsInfo.snapshots`.
  - `ZfsInfo.clones` comes from the snapshot's own `clones` column, which is complete for a named snapshot.
- Flag unset: the commands and their argument order are unchanged, and every call site passes `recursive=true`.

Main code: ZfsCommands, ZfsUtils, ZfsProvider: +178/−30 lines. Tests: +~170.

## Expected effect
The suspend-io window of a clone loses the source's snapshot walks: ~4.1 s → ~0.6-0.9 s idle. What remains is the controller round trips, the two targeted lists (~10-20 ms), the snapshots and resume-io.

The window cannot go below the three-step protocol: all diskful nodes must be suspended while their CF_ snapshots are taken, or the clone's replicas differ while DRBD treats them as in sync.

Outside the window, every device manager run on a node with heavily cloned sources stops paying ~0.8 s per source and call.
