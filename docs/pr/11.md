# drbd: do not skip the initial sync on a backing device the satellite did not create

Refs: LINBIT/linstor-server#551 (related: #545, #546, #548)

## Problem

If a backing device already exists under the name LINSTOR uses for a volume,
`resource create` adopts it without creating a new one. One way this happens
is a zvol left behind by a busy `zfs destroy` (#545). On thin storage, DRBD
then skips the initial sync and declares the replica UpToDate, although the
adopted device has unknown content.

Repro on a 2-node 1.35.2 cluster (ZFS thin, details in #551): an adopted zvol
with 64 MiB of random data was declared UpToDate on both nodes, and
`drbdadm verify` found 16,384 out-of-sync 4 KiB blocks. The replicas silently
diverged.

## Cause

References are to master e1d99946e.

- A volume is only created in `AbsStorageProvider.createVolumes` (create,
  snapshot restore or clone, ending in `vlmData.setExists(true)`). A dataset
  found in `zfs list` under the expected name skips that and is treated as
  existing (`ZfsProvider.updateState`/`updateInfo`). Nothing records that it
  was not created by this satellite.
- `DrbdLayer.createMetaData` skips the initial sync for a thin loser
  (`DrbdLayerUtils.skipInitSync`, `DrbdLayer.java:1569` on master): it injects
  the day0 GI and marks the volume UpToDate. That is only correct for a
  freshly created thin device, whose unwritten blocks read as zeroes.

## Fix

- `AbsStorageVlmData` gets a transient satellite-only flag `createdByStlt`
  (`server/.../storage/data/provider/AbsStorageVlmData.java:53`).
  `AbsStorageProvider.createVolumes` sets it right after
  `vlmData.setExists(true)` (`AbsStorageProvider.java:763`), so it covers
  create, restore and clone, and only those.
- `DrbdLayer.createMetaData` checks all storage devices of the data child
  (`DrbdLayer.isCreatedByStlt`, `:1659`; used at `:1554`):
  - A thin loser skips the initial sync only if every device was created by
    this satellite (`:1584`). Otherwise its metadata stays just-created, as
    for thick volumes, so it does a full sync from the UpToDate peers. A
    warning names the volume.
  - A winner on an adopted device only logs a warning that the device's
    current content becomes the initial UpToDate data. See "Open point".
- Devices of providers that are not `AbsStorageVlmData` are not tracked and
  count as created, so their behaviour is unchanged.

The flag is not persisted. If the satellite restarts between creating the
device and creating the DRBD metadata, or the layer data object is rebuilt,
the device counts as adopted and gets a full sync. That is the safe
direction. Once DRBD metadata exists, `createMetaData` is not called, so
existing resources are not affected.

Not in this PR (see #551): refusing or renaming an adopted device, comparing
`volblocksize` with `StorDriver/ZfscreateOptions`, and an ownership marker
(e.g. a `linstor:` user property with the volume UUID).

### Open point: adopted device on the race winner

If the adopted device is on the node that wins the UpToDate race, the winner
gets current=random and bitmap=day0, and thin losers get current=day0. The
losers then resync only blocks written after day0, so old content on the
winner that differs from the zeroed losers is still not synced. This PR only
logs a warning for that case. Fixing it needs a decision on the GI layout,
for example no day0 relation from a winner on an adopted device, which forces
a full sync to the peers. That should be tested on the rack first.

Merge note: this touches the same block of `DrbdLayer.createMetaData` as the
fix for #548 (branch `fix/linstor-server-5-thin-readd-no-gi`). Whichever is
merged second needs a trivial rebase.
