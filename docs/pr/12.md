# drbd,zfs: refuse an adopted zvol whose volblocksize differs from ZfscreateOptions

Refs: LINBIT/linstor-server#551. Builds on `fix/linstor-server-11-adopted-device-sync`.

## Problem

A zvol that already exists under the name LINSTOR uses for a volume is
adopted on `resource create` instead of being created (#551). It keeps its
`volblocksize`, and an explicit `-b` in `StorDriver/ZfscreateOptions` is
silently ignored. In the #551 repro, a zvol created by hand with `-b 8K` was
adopted although the volume definition requested `-b 16K`. No message
mentioned it.

## Cause

`ZfscreateOptions` is only applied in `ZfsProvider.createLvImpl`, i.e. by
`zfs create`. An adopted zvol never gets there (see the cause section of
the #551 fix). Nothing compares the existing dataset with the requested
options.

## Fix

References are to this branch.

- `ZfsUtils.getRequestedVolBlockSize` (`satellite/.../zfs/utils/ZfsUtils.java:571`)
  returns the `volblocksize` explicitly requested by the "zfs create"
  options (`-b SIZE`, `-bSIZE`, `-o volblocksize=SIZE`; K/M/G as powers of
  1024, no suffix = bytes), or null.
- `ZfsProvider.updateStates` (`ZfsProvider.java:857`) records it on the
  volume's `ZfsData` (new transient field, `server/.../zfs/ZfsData.java:41`).
  This only records it and never refuses anything.
- `DrbdLayer.createMetaData` calls `checkAdoptedZfsDevices` (`DrbdLayer.java:1498`,
  `:1663`) before `create-md`. For each ZFS storage device of the data child
  that was not created by this satellite (the #551 flag):
  - if a `volblocksize` is explicitly requested and the zvol's actual one
    (from `zfs list`) differs, it throws a `StorageException` naming the
    dataset and both values, with the correction "remove or rename the
    existing dataset, or adjust ZfscreateOptions". The resource stays in
    error and no DRBD metadata is created;
  - if the zvol's size differs from the expected size, it logs a warning
    naming both sizes.

### A refused device must not block deletes and is never destroyed

A refused device was never created by LINSTOR, so the refusal sets a
transient marker (`AbsStorageVlmData.adoptionRefused`):

- Later runs do not fail again. `DrbdLayer.process` skips the adjust of the
  resource with a warning ("still refusing to adopt ..."), and clears the
  marker once the mismatch is gone. Without this, `resource-definition
  delete` got stuck: it updates the satellite before it marks the resource
  for deletion, and every run refused again with an error.
- While the resource definition is being deleted, an adopted mismatching
  device of a resource whose DRBD resource is not up is refused the same way,
  without an error. This covers a satellite restart between refusal and
  delete, and never writes DRBD metadata onto the foreign device.
- The storage delete path forgets a refused device (`exists=false`) and does
  not run `zfs destroy` on it (`AbsStorageProvider`, next to the existing
  "needed by shared resource" case).
- A refused volume is not created while it, its volume definition, its
  resource or its resource definition is being deleted. Otherwise, if the
  foreign zvol was removed meanwhile, the delete first created a fresh zvol
  and DRBD metadata, only to delete them again.
- Creating the device itself (e.g. after the user removed the dataset and
  the resource is not being deleted) clears the marker.

Limitation: the marker is not persisted. After a satellite restart a
resource-definition delete sets it again, but a per-node `resource delete`
does not, and then destroys the adopted device as before. A persistent
ownership marker (e.g. a `linstor:` user property with the volume UUID, see
#551) is the proper fix.

### Why the check is in `createMetaData` and not in `ZfsProvider.updateState`

`updateState` runs every cycle for every listed zvol. The "created by this
satellite" flag is not persisted, so after any satellite restart every
existing zvol looks adopted. A rule there would refuse healthy volumes, for
example after a restart or after `ZfscreateOptions` was changed on the
resource group after the volumes were created. `createMetaData` only runs
when DRBD finds no metadata, i.e. for a new replica, so existing volumes are
never refused.

### Limitations

- Only resources with a DRBD layer are checked. A storage-only resource
  still adopts the zvol silently.
- Only `volblocksize` is compared. Other create options are not.
- Refusing or renaming every adopted dataset (#551) and an ownership marker
  are still open.

Deployment note: like the #551 fix, this changes `ZfsData` in the shared
server module. The satellite and server jars must come from the same build.

## Dev-rack result

First run (before the delete fix), 1.35.2 + DRBD 9.3.4, 2 diskful nodes,
adopted 8K zvol with 64 MiB of data on the second node, `-b 16K`:

- `resource create` on that node failed as intended. The error report says
  "Meta data creation ... refused", names the dataset with 8 KiB vs 16384
  bytes, and gives the correction. The DeviceManager kept running.
- Control without `-b`: the same as without this change (warning, full
  initial sync, `drbdadm verify` 0 out of sync).
- Gap found: the following `resource-definition delete` did not complete
  (stuck in DELETE for more than 120 s, the refusing node refused again in
  every run). After the foreign zvol was removed by hand, the delete first
  created a fresh 16K zvol and DRBD metadata, then deleted them. Both are
  fixed above.

Rerun with the delete fix (same setup, satellite and server jars from one
build of v1.35.2 plus this branch, #551 and #545):

| Case | Result |
|---|---|
| `resource create` on the node with the adopted 8K zvol, `-b 16K` | refused once (one error report naming dataset, 8 KiB vs 16384 bytes, correction); later runs only log "still refusing to adopt ... the DRBD resource stays unconfigured", no further error reports; DeviceManager keeps running |
| `resource-definition delete` after the refusal | completes in one call (2 s); satellite logs "will not be deleted as it was not created by LINSTOR and its adoption was refused; only forgetting it"; `zpool history` shows no `zfs destroy` and no new `zfs create`, the foreign zvol is untouched |
| control without `-b` | as without this change: warning, full initial sync, `drbdadm verify` 0 out of sync |

Not run on the rack: the foreign zvol disappearing while the delete is
running (covered by `ZfsProviderAdoptedZvolTest`), and a satellite restart
between refusal and delete (see "Limitation" above).

Follow-up: a persistent ownership marker for datasets created by LINSTOR
(e.g. a `linstor:` user property with the volume UUID, #551). It would close
the restart limitation and allow refusing or renaming any adopted dataset,
not only one with a mismatching `volblocksize`.
