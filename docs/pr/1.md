# zfs: retry "dataset is busy" on destroy with bounded backoff

Refs: LINBIT/linstor-server#545

## Problem

On `resource delete`, `resource-definition delete` and `resource toggle-disk --diskless`
with a ZFS (thin) storage pool, the satellite runs `zfs destroy` right after
`drbdsetup down`. It gets `cannot destroy ...: dataset is busy` and the
resource stays `DELETING` (or `Diskless, Removing Disk`) until something else
makes the device manager run again. A moment later nothing holds the zvol, and
a manual `zfs destroy` succeeds. This happened in 6 of 8 deletes during one
storage-node drain (LINSTOR 1.35.2, OpenZFS 2.4.4, DRBD 9.3.4).

Additional consequence observed 2026-10-24: after a `resource delete` whose `zfs destroy` failed with 'dataset is busy', a subsequent `resource create` on the same node reattached the surviving zvol instead of creating a new one (the vd-level StorDriver/ZfscreateOptions were ignored), and the resource reported UpToDate after a resync, so the stale block device silently survives a recreate. Timing seen on the satellite: DRBD down, size probe of the zvol 20 ms later, destroy 0.45 s after the DRBD delete while the kernel was still releasing the backing device; 3 of 4 destroys of written zvols hit the race on the first attempt, empty zvols never did. The retry only happened at the next DeviceManager cycle triggered by an unrelated event.

## Cause

The destroy is retried, but only for about 0.3 s:

- `ZfsProvider.deleteCascading` (`satellite/.../layer/storage/zfs/ZfsProvider.java:495`)
  calls `ZfsCommands.delete(extCmd, fullQualifiedIdentifier, type)`.
- That overload (`satellite/.../layer/storage/zfs/utils/ZfsCommands.java:123-127`
  on upstream master e1d99946e; same for the zpool/identifier overload at `:105-109`)
  uses `new RetryIfDeviceBusy()`.
- `RetryIfDeviceBusy` (`satellite/.../layer/storage/utils/RetryIfDeviceBusy.java:10-11`)
  defaults to 3 retries with a constant 100 ms delay, so a dataset that is busy
  for more than about 0.3 s after `drbdsetup down` makes the delete fail.

The window we saw is longer than 0.3 s but short: "nothing holds it a moment
later".

## Fix

- `RetryIfDeviceBusy` gets an optional backoff: the constructor
  `(count, delayInitialInMs, delayMaxInMs)` doubles the delay after each retry
  up to `delayMaxInMs`. The existing constructors keep the constant 100 ms
  delay, so LVM (`LvmCommands`) and SPDK (`SpdkLocalCommands`) behave as before.
  A `Sleeper` parameter (default `Thread::sleep`) is the test seam.
- `ZfsCommands` defines named constants for the destroy retry and uses them in
  both default `delete` overloads:
  - `DESTROY_RETRY_COUNT = 6`
  - `DESTROY_RETRY_DELAY_INITIAL_IN_MS = 200`
  - `DESTROY_RETRY_DELAY_MAX_IN_MS = 2_000`

  Retry delays: 200, 400, 800, 1600, 2000, 2000 ms. That is 6 retries (7 attempts
  in total) over at most 7 s of waiting, compared to 3 retries over 0.3 s
  before. A dataset that stays busy still fails after that, as before, so the
  device manager is blocked for at most 7 s per volume.
- The retry still only happens when stderr contains "busy". Other errors fail
  immediately, as before.

Alternative considered: wait for the DRBD minor to disappear before
`zfs destroy`, as the issue also suggests. That would need the DRBD layer to
signal the storage layer (or the storage layer to know about DRBD minors),
which is a larger change across layers. The bounded retry is the smaller
change and also covers other short-lived holders of the zvol, such as udev.

## Tests run

Environment: OpenJDK 21.0 (openjdk-21-jdk-headless), Gradle wrapper,
protoc 31.1 via `./gradlew getProtoc`, linstor-common submodule at d2eb4e8bb.

- `./gradlew assemble`: BUILD SUCCESSFUL.
- `./gradlew :satellite:test`: BUILD SUCCESSFUL, 143 tests, 0 failures,
  0 errors, 0 skipped. That includes the new tests:
  - `RetryIfDeviceBusyTest` (4): backoff sequence 200/400/800/1600/2000/2000 ms
    and then stop, no retry on a non-busy error, constant 100 ms for the old
    defaults, never skip.
  - `ZfsCommandsDestroyRetryTest` (3, mocked `ExtCmd`, fake sleeper):
    busy 6 times then ok gives 7 execs and success; busy 7 times gives 7 execs
    and a `StorageException`; a non-busy error gives 1 exec, an exception and
    no sleep.
  - With the destroy constants set back to the old 3 × 100 ms,
    `destroySucceedsOnLastRetry` fails, so the test catches the bug.
- `./gradlew :satellite:checkstyleMain :satellite:checkstyleTest`: BUILD
  SUCCESSFUL. No new warnings in main code (the import-order and comment
  indentation warnings in `ZfsCommands.java` were there before). The new tests
  have the same `magicnumber` warnings as the existing satellite tests.
- Not run: anything against real ZFS/DRBD (no storage on this machine), and
  the controller/server test suites (`:satellite` only, as requested).
