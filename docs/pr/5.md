# drbd: thin replica added after initialization without day0 GI syncs from peers

Refs: LINBIT/linstor-server#548

## Problem

On thin pools, re-adding a replica to a resource that already has UpToDate
peers (`linstor r create <node> <res>`, `linstor r toggle-disk <node> <res>`)
fails its first metadata creation when the volume definition has no
`DrbdCurrentGi`. The API returns `Meta data creation ... failed ... volume uses
a thin provisioning storage driver, but no initial value for the DRBD current
generation is set on the volume definition`, and an error report is written.
About a minute later the device manager retries, and the replica comes up
Inconsistent and does a correct full resync. This happened for 8 of 8
resources in one node rejoin. Tooling that treats the API error as fatal stops
at that point.

## Cause

References are to upstream master e1d99946e,
`satellite/src/main/java/com/linbit/linstor/layer/drbd/DrbdLayer.java`:

- `createMetaData` (`:1490`) runs `drbdUtils.createMd(...)` first (`:1536`).
- A thin volume that did not win the UpToDate race takes the
  `DrbdLayerUtils.skipInitSync(drbdVlmData)` branch (`:1569`).
- That branch calls `getCurrentGiFromVlmDfnProp` (`:1655`), which throws a
  `StorageException` when `DrbdCurrentGi` is not set (`:1671`, message at
  `:1679`). The volume definition's `DRBD_INITIALIZED` flag is not checked.
- The exception comes after `create-md` has already run. On the next device
  manager run, `hasMetaData` is true (`:706`), so `createMetaData` is skipped.
  The metadata stays in its just-created state, and DRBD does a full sync from
  the UpToDate peers. That is why the retry gets the right end state.

Background: the loser's day0 GI was introduced in 0e1bc18b7 ("Drbd,UpToDate:
Changed method how vlms are set UpToDate"), and marked UpToDate again in
0024071e4 ("LvmThin: Set all thin volumes UpToDate again", for DRBD 9.3.2's
skip-initial-sync heuristic). Both commit messages describe the initial
creation of a resource. `DRBD_INITIALIZED` is set once the initial winner has
reported UpToDate (`controller/.../internal/VlmDfnInternalCallHandler.java:138`).

## Fix

In `createMetaData`, a thin loser uses the day0 GI only if
`useDay0GiAsLoser(vlmDfnDrbdInitialized, hasCurrentGi)` holds:

| `DRBD_INITIALIZED` | `DrbdCurrentGi` set | result |
|---|---|---|
| no  | yes | day0 GI (unchanged) |
| no  | no  | day0 GI path, still fails as before: the GI is required for initial creation |
| yes | yes | day0 GI (unchanged) |
| yes | no  | **new:** metadata stays just-created, full sync from the UpToDate peers, one info log line |

The new case gives the same end state as today's retry, without the failed
first attempt, the API error and the error report. Thick volumes are not
affected.

Not changed: the case where a GI is present (row 3). #546 reports that a stale
GI copied from a ZFS clone source produces a bogus day-0 UpToDate replica.
Skipping day0 for every initialized volume definition would undo part of
0024071e4 for all thin volumes added later, so we treat that as a design
question for LINBIT rather than include it here.
