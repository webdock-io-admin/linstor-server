# Fix 22: one superblock write instead of 31 drbdmeta set-gi calls on the UpToDate-race winner

Base: fix 21 (eec125c9c) on the v3-r2 set (v1.35.3 + fix 16 + #545 + fix 20).

## Problem
`DrbdLayer.createMetaData()` runs `drbdmeta --force --node-id N <minor> v09 <dev> internal set-gi <gi>` for N = 0..31 on the node that wins the initial UpToDate race (`hasLocalStltWonUpToDateRace()`). The local node-id gets `<random>:<day0>::::1:1` and each other node-id gets `:<day0>::::`.
- Each call is a synchronous read-modify-write of the same 4 KiB superblock.
- On our dev pair under ~0.5 GB/s of writes per node, the gap between "DRBD meta data created" and "DRBD skipping initial sync" was 194-213 s for one new volume. Each call waits ~6 s for a ZFS txg sync.
- All of it runs on the DeviceManager thread, so every other resource on that node waits too.
- Clones are not affected: they run no set-gi.

## Why every node-id and not only the peer slots
drbdmeta's `peers[]` is indexed by node-id. set-gi allocates no bitmap slot (bitmap_index stays -1). The day0 bitmap UUID on a node-id is what lets a future peer with that id start from the day0 bitmap instead of a full sync. LINSTOR hands out the lowest free node-id, so any id can appear later.

## Fix
- `DrbdMdV09PeerBitmapUuids` reads the v09 superblock and sets `peers[n].bitmap_uuid` for every node-id n except the local one. It then writes the superblock back once (FileChannel, DSYNC + force).
  - Location: internal md uses the last 4 KiB-aligned block, flex-external offset 0.
  - Offsets follow drbd-headers `struct meta_data_on_disk_9` / `peer_dev_md_on_disk_9`: magic at 60 (0x8374026D = DRBD_MAGIC + 6), peers at 112, 32 bytes each, bitmap_uuid at +0. All big endian.
  - It refuses a superblock without the v09 magic.
- In `createMetaData()`, if this is enabled and the GI for the other node-ids is a pure bitmap-UUID GI (`DrbdGiStringBuilder.getBitmapUuidIfOnlyField()`), that write replaces their 31 set-gi calls. The local node-id still gets its drbdmeta set-gi afterwards, which re-reads, validates and rewrites the superblock (feature mask, lkbd update) as before.
- Any exception: an error report, then the existing loop for all node-ids.
- **Off by default.** Enable on a satellite with the environment variable `LINSTOR_SATELLITE_SETGI_SINGLE_WRITE=true`, e.g. in a systemd drop-in for linstor-satellite.

## Expected effect
For a new race-winner volume, 32 synchronous md writes become 2 (ours plus the local set-gi). Under the measured load that is ~200 s → ~12 s, and ~5 s → ~0.3 s idle.

## Tests
- `DrbdMdV09PeerBitmapUuidsTest` (5): only the 31 bitmap_uuid fields change (byte check), magic check, offset, internal/external file write, GI qualification.
- `DrbdMdV09PeerBitmapUuidsDrbdmetaTest` (2): uses a real drbdmeta 9.35.0 (`LINSTOR_TEST_DRBDMETA`, skipped if unset) on 64 MiB files, with the exact command line DrbdAdm.setGi uses. The 32-call loop and the new path give identical `dump-md` output for internal metadata with local node-ids 0, 1, 9, 31, and for flex-external metadata. The comparison is at dump level: until the local set-gi rewrites the superblock, the reserved and padding bytes may differ.
- `./gradlew :satellite:test`: 162 tests, 0 failures. `./gradlew :test`: 2,214 tests, 0 failures. No new checkstyle warnings in main code.
- Review: one adversarial pass (Qwen), then verified here. No correctness findings. Applied: explicit big-endian order, NODE_ID_COUNT tied to NodeId.NODE_ID_MAX, comments citing the drbd-headers constants.
