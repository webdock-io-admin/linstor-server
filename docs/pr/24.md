## Problem
A REST answer is rendered and written synchronously on the `MainWorkerPool` thread that holds a satellite peer's in-order turn (`apiCallComplete` → `RequestHelper.doFlux` → `asyncResponse::resume`). That pool has `bounds(4, CPU_COUNT, 16)` threads.

If the HTTP client stops reading without an RST, the write blocks in Grizzly for up to its write timeout (30 s default). Other workers with messages from that peer spin in `processInOrder`, the pool is exhausted, and answers from every satellite stall.

Seen on our dev cluster on 2026-11-07, and reproduced on 2026-11-08 with all satellites online: all 5 clones parked, and the controller had to be restarted. Details in #572.

## Fix
- **D:** `publishOn` a bounded-elastic `RestResponse` scheduler (16 threads, 32 queued tasks; `ControllerCoreModule`) before `subscribe(asyncResponse::resume…)`.
  - Sites: `RequestHelper.doFlux` and the four `BackupShippingInternal` sites.
  - A full queue makes `publishOn` reject. Reactor 3.8.8 `FluxPublishOn.trySchedule` catches the `RejectedExecutionException` and signals `onError` (checked in bytecode), so `resumeWithError` answers 503 with `Retry-After: 5`.
- **D2:** Grizzly transport write timeout of 10 s on every listener (`GrizzlyHttpService.enableFeatures`, before start).
  - The wait it bounds is per stalled flush (`OutputBuffer.blockAfterWriteIfNeeded` waits only while the async write queue is full). A slow client that keeps reading does not hit it.
- **E0:** `RequestHelper.offWorker()` = `publishOn(RestResponse)` before the JSON render in the satellite-fed list endpoints:
  - View resources and storage pools;
  - Volumes;
  - per-node StoragePools.
- **A:** `SatelliteCallGuard` in `FreeCapacityFetcherProto`, `VlmAllocatedFetcherProto` and `CtrlErrorListApiCallHandler`.
  - It skips peers that are not online.
  - Each node's answer has a timeout: controller prop `Ctrl/SatelliteCallTimeoutSec`, or `Aux/SatelliteCallTimeoutSec`, default 30 s.
  - PeerNotConnected, PeerClosingConnection, ApiCallNoResponse and timeout become "no data" with a warning.

## Review (Qwen adversarial pass, checked here)
- **Not real:**
  - "rejection escapes subscribe synchronously" (see D above);
  - `logWarning` missing, JUnit 4 classes and missing imports: the main and test sources compile;
  - "10 s aborts slow live clients" (see D2 above).
- **Real, documented, not changed:**
  - A widens what counts as "no data". An online but hung satellite now gives empty free-space/allocated answers, keeping the previous values, plus a warning.
  - An error-report delete on a timed-out node contributes no result.
  - Under E0 each covered list response takes two hops on the RestResponse scheduler, so the 32-task queue is shared by roughly 16 in-flight list answers plus everything else. Bursts beyond that get 503 instead of queueing, which is intended.
  - Log lines written on the response side lose the MDC (cosmetic).
  - `SatelliteCallGuardTest.silentSatelliteBecomesEmptyAfterTimeout` has an upper bound of 5 s and could be flaky on a loaded CI.
- **Fixed:** an errorprone `JavaDurationGetSecondsToToSeconds` failure (`-Werror`) in `SatelliteCallGuard`.
