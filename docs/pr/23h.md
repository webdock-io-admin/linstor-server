# Fix 23h: the allocated-size query lists only the queried volumes

Base: fix 23e (branch fix/linstor-server-23e-targeted-zfs-list), whose non-recursive `zfs list` this reuses.

## Problem
`GET /v1/view/resources`, which `linstor resource list` uses, has no cache. On every call the controller sends `API_REQUEST_VLM_ALLOCATED` to every satellite with thin storage pools and waits for all answers (`VlmAllocatedFetcherProto`, `CtrlVlmListApiCallHandler.listVlms`).

On a satellite, ZFS answers with `ZfsProvider.fetchAllocatedSizes()`, which ran the default recursive listing over all of its thin volumes: `zfs list -r … -t volume,snapshot`. That walks every snapshot of every volume, although only the volumes' allocated sizes are used.

On our dev cluster, storage nodes hold image resources with about 1,900 snapshots per volume, and 2,000+ resources in total. There:
- one `linstor resource list` took about 300 s on a satellite that had been running for 27 h;
- `/v1/view/resources` hung for more than 180 s after a controller start, while `/v1/nodes` answered in 20 ms.

## Cause
satellite/.../zfs/ZfsProvider.java:1091-1110 (before this fix) called `ZfsUtils.getZfsList(extCmdFactory, dataSets, kind, emptyMap())`. That is the recursive overload, so its cost grows with the snapshot count of the listed volumes.

## Fix
- `ZfsUtils.listDatasets(extCmdFactory, datasets, kind)` (ZfsUtils.java:274) lists exactly the given datasets: one `zfs list` without `-r`, no origin lookup, no property query. It is built on the same non-recursive listing fix 23e added.
- `fetchAllocatedSizes()` uses it (ZfsProvider.java:1107).
- A volume that is not listed keeps its previous allocated size, as before.
- No flag. The result is the same for every queried volume, because the allocated size of a volume (`refer` for ZFS_THIN, `volsize` for ZFS) does not depend on its snapshots being listed.
