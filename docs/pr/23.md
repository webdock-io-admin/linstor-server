# Fix 22b/23: keep the backing devices open while drbdmeta / drbdadm run on them

Base: fix 22 (813b17687) on fix 21 on the v3-r2 set (v1.35.3 + fix 16 + #545 + fix 20).

## Problem (measured on our dev cluster, loaded ZFS pool, 2026-11-05)
- Each `drbdmeta` call on a zvol cost ~4.5 s (2-9 s). The I/O is tiny: a few reads, one pwrite, 2 fsyncs of ~4 ms. The time is all in `close()` of the zvol.
- Kernel stack: `close → zvol_release → zvol_last_close → zvol_shutdown_zv → txg_wait_synced` (directly or via `zil_close`). A following open can block on the bdev open mutex behind such a close.
- Every last close of a zvol waits for a txg sync. The create path closes the zvol many times before the kernel's `drbdsetup attach` holds it open:
  - a new race-winner volume: 32 set-gi calls;
  - every volume, clones included: md check, get-gi, check-resize, repair-md, apply-al.
- Held-fd test (u1r8): with one O_RDONLY fd held on the zvol, close() per set-gi went 4.53 s → 0.0 ms. "meta data created" → "skipping initial sync" went 138-156 s → 1.7-1.8 s, and a whole bare create under load went 179-197 s → 10-28 s.

## Change
- `BackingDeviceHold` keeps plain read-only FileChannels (no O_EXCL) open and closes them in `close()`. Null, missing or unopenable paths are skipped; a skip is logged at INFO.
- `DrbdLayer.adjustDrbd()` now wraps the existing method in `try (BackingDeviceHold hold = …)`. Right after the child (storage) layer has processed the resource, it opens every diskful volume's data device and external meta device, only for a diskful resource without skip-disk. The hold then lasts through the md checks, createMetaData (set-gi), the res-file render and `drbdadm adjust`.
  - After a successful attach the kernel holds the device, so the hold's own close is cheap.
  - If attach never happens, it pays one last-close per device, once.
- `processAfterClone()`: the same hold around `drbdmeta check-resize`; that runs on the CloneService thread.
- Storage operations (zfs create/destroy/resize, rollback deletes) all run in `processChild()`, before the hold is taken, and no delete runs inside it.
- **Off by default.** Enable with `LINSTOR_SATELLITE_HOLD_BACKING_DEVICES=true` in the satellite's environment. It is independent of fix 22's `LINSTOR_SATELLITE_SETGI_SINGLE_WRITE`; with this hold on, fix 22 is not needed.

## Risk
- External tools (admin `zfs rollback`/`destroy`, `lvremove`, `dmsetup remove`) get EBUSY on that backing device for the duration of one adjust, where before they could slip in between drbdmeta calls.
- On a failed attach, the one remaining last close per device lands on the DeviceManager thread.
- The kernel's exclusive claim (`drbdsetup attach`) next to a plain open is expected to be fine, since bd_prepare_to_claim ignores non-exclusive openers. It is not testable here without block devices; rack test 2 below covers it.

## Tests
- `BackingDeviceHoldTest` (6): opens existing paths, skips null/missing; released on exception; no fd leak over 50 rounds (/proc/self/fd); device removed while held closes cleanly; disabled hold opens nothing; unreadable device skipped.
- `DrbdMdV09PeerBitmapUuidsDrbdmetaTest.drbdmetaWorksWhileTheDeviceIsHeld`: create-md, set-gi and dump-md with real drbdmeta 9.35.0 while the hold is open. This is on a regular file, so the block-layer claim is not exercised.
- `./gradlew :satellite:test`: 169 tests, 0 failures. No new checkstyle warnings in main code.
- Review: one adversarial pass (Qwen), then verified here. Applied: hold only for diskful resources without skip-disk, and skipped opens logged at INFO. Checked and fine: delete ordering, device selection over LUKS/writecache/external md, fd lifecycle, thread confinement, and the clone hold's path (the data device for internal md).

## Rack tests (not run here)
