# Fix 26: finish a resource-definition delete after a successful resource retry

Upstream issue: draft `linstor-rd-delete-not-finalised-after-retry.md` (not posted yet). Base: fix 24b (161ca9d4f). Commit: 70655fa9a. Controller only.

## Problem
`resource-definition delete` whose first answer from a satellite is an error leaves the rd flagged `DELETE` with no resources, until a satellite reconnects or the delete is issued again.
- Here the error was a busy `zfs destroy` (#545). The satellite destroyed the zvol on its own next run, and the controller's retry removed the resources.
- Dev rack, 2026-11-10: 4 of 4 busy-first deletes stuck, for 2-14 min until someone re-issued the delete; 3 of 3 clean deletes were fine.
- It happened both with and without a controller fail-over.

## Cause (1.35.3)
- `CtrlRscDfnDeleteApiCallHandler.deleteResourceDefinitionInTransaction` returns `truncate(...).concatWith(deleteData).onErrorResume(DelayedApiRcException -> empty)`. A satellite error ends the truncate, so `deleteData` is skipped and the error is swallowed.
- `CtrlSatelliteUpdateCaller.updateResource` puts the failed resource into `RetryResourcesTask` with the per-resource next step only (`cleanupAndDelete`).
- The retry removes the resource, and nothing removes the rd. `resourceDefinitionConnected` restarts the delete only on a satellite reconnect.

## Fix
- `CtrlRscDfnDeleteApiCallHandler.finishDeleteIfFlagged(rscName)`: under the rd-map write lock, if the rd exists and is flagged `DELETE`, run `deleteResourceDefinitionInTransaction`. That is the same path as the reconnect hook and a re-issued delete.
- `RetryResourcesTask`: after the satellite's answer to a retry and the next step, call it if the answer had no error entries. A retry that fails again leaves the rd alone.
- The retry flux moves into a package-private `retryFlux()` for tests. It is otherwise unchanged.

## Review (Qwen adversarial pass, checked here)
- **Not real:** "the `isDeleted()` guard skips the stuck rd". `markDeleted()` only sets the `DELETE` flag (ResourceDefinition.java); `isDeleted()` becomes true only after `delete()` removed the object. The handler test seeds exactly the stuck state (flag set, no resources) and passes.
- **Real, documented, not changed:**
  - Pre-existing upstream behaviour: the retry runs its stored next step even when the satellite's answer has errors (`.concatWith(nextStep)` is not gated). The controller can then remove a resource whose backing device is still there on the satellite, which may explain the orphan zvol seen on 11-07. Fix 26 gates only its own step. Gating the next step is a separate change with more callers (toggle-disk, activation, and so on).
  - An answer with no entries counts as success. The re-run delete then simply fails again if the satellite was not done, the same as a manual re-issue.
  - The result of the finish step goes where the retry's results always went (subscribed and dropped). Its errors are not reported separately.
  - If a user re-issues the delete at the same time, both runs take the rd-map write lock one after the other. The second finds the rd gone and does nothing.
  - An rd flagged `DELETE` means its delete was requested. Finishing it from a retry of any of its resources (also after a per-node delete or a toggle-disk retry) is the intended outcome.
- **Not real:** a DI cycle. The task takes a `Provider<CtrlRscDfnDeleteApiCallHandler>`, like CtrlSnapshotDeleteApiCallHandler does.

## Tests
- New `RetryResourcesTaskFinishDeleteTest` (3), with mocked peer and handler and a satellite answer serialized as protobuf `ApiCallResponse`:
  - a successful retry runs the next step, then finishes the rd delete;
  - a retry answered with "dataset is busy" (FAIL_UNKNOWN_ERROR) does not touch the rd;
  - a peer error ends the retry without finishing.
- `CtrlRscDfnDeleteApiCallHandlerTest` +3 (now 9): a flagged empty rd is deleted; an unflagged rd is kept; a missing rd is a no-op.
