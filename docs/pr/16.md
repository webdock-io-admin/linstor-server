# zfs: scope the satellite's listings to the datasets it acts on

Refs: #309 (fixed in v1.20.0 by 473795540, see "Relation to #309" below)

## Problem

On a ZFS storage node the satellite's own `zfs list` / `zfs get` calls cost time
proportional to every zvol and snapshot in the pool, even when it acts on one
resource or on none.

An exec trace of an idle LINSTOR 1.35.2 satellite (2 minutes, 159 zvols and
110 snapshots in the pool, storage node of a 6-node dev cluster) showed per
idle minute:

- about 9 × `zfs list -r -H -p -o name,refer,volsize,type,volblocksize,origin,clones -t volume,snapshot`
  **without a dataset argument**, which walks every pool, zvol and snapshot on
  the host;
- about 13 × `zfs get -r -o name,value -H -p -s local linstor:marked_for_deletion <pool>`,
  recursive over the whole pool including all snapshots;
- about 13 × the per-resource `zfs list -r … -t volume,snapshot <volumes>`;
- about 15 × `zfs list -r -t filesystem <pool>`.

Warm, each pool-wide call took 83 ms for 269 datasets, about 0.31 ms per
dataset. With about 22 pool-wide scans per idle minute, the satellite's own
listings fill a whole minute at about 4,400 datasets per node, before any
create, delete or resync:

| datasets/node | one scan | idle scan time per minute |
|---|---|---|
| 300 | 93 ms | 2.0 s |
| 1,000 | 0.31 s | 6.8 s |
| 2,000 | 0.62 s | 13.6 s |
| 4,400 | 1.36 s | 30 s |
| 8,000 | 2.5 s | 54 s |

This is the warm case. Snapshots and detached zvols are not owned by anyone, so
OpenZFS reloads their metadata on every list; on a 13K-dataset host a single
`zfs list` took 38-49 s. With `UseZFSClone`, every clone keeps a `CF_*`
snapshot of its source volume, so a node with thousands of clones carries
thousands of snapshots that every pool-wide scan visits.

## Cause (master e1d99946e)

1. **`zfs list` without a dataset argument.**
   `Commands.genericExecutorLimiter` (`server/.../storage/utils/Commands.java:157`)
   runs `(size / ARGUMENT_LIMIT) + 1` batches. For an empty collection that is
   one call with no dataset argument, and for exactly 1000, 2000, … datasets the
   last batch is empty. `zfs list -r` without a dataset lists everything on
   the host. Its only user is `ZfsCommands.list` (`satellite/.../zfs/utils/ZfsCommands.java:27`).
   The code is the same on master e1d99946e and on v1.35.2, so both are affected.
   `ZfsProvider.fetchAllocatedSizes` (`ZfsProvider.java:1033`, called from
   `StltApiCallHandlerUtils.java:164` for every thin storage pool) passes an
   empty set when a thin pool has no volume matching the query's resource
   filter.
2. **`marked_for_deletion` read for the whole pool.** `ZfsUtils.getZfsList`
   (`ZfsUtils.java:177-203`) lists the given datasets, then runs
   `zfs get -r … linstor:marked_for_deletion <zpool>` on the zpools of those
   datasets (`ZfsProvider.getZPoolDataSets`, `ZfsProvider.java:162`). The
   result is only applied to datasets that the `zfs list` returned
   (`infoByIdentifier.get(…)`); everything else in the pool is read and
   discarded. This runs in every `prepare()` of the ZFS providers, i.e. every
   device manager run that touches a ZFS resource.
3. **Thin pool space query recurses into the pool.** `ZfsCommands.listThinPools`
   (`ZfsCommands.java:350`) uses `zfs list -r -t filesystem <pool>`. All three
   callers (`ZfsThinProvider.checkConfig`/`getSpaceInfo`, `ZfsProvider.checkConfig`)
   only look up `<pool>` itself, but `-r` makes ZFS open every zvol below it to
   check its type.

## Fix

- `genericExecutorLimiter` runs `ceil(size / ARGUMENT_LIMIT)` batches, so an
  empty collection runs no command and there is no trailing empty batch.
- `getZfsList` runs the recursive property query on the datasets the
  `zfs list` returned: each listed volume (its snapshots come with `-r`) and
  each listed snapshot whose volume was not listed. That is exactly the set
  the result is applied to. `getUserProperty` now goes through
  `genericExecutorLimiter` (batches of 1000) and allows exit code 1, like
  `list`: a dataset destroyed between the list and the get does not fail the
  run. The now unused `poolDatasets` parameter and
  `ZfsProvider.getZPoolDataSets` are removed.
- `listThinPools` uses `-d 0` instead of `-r`: only the named datasets.

After the change, a device manager run's ZFS calls cost time proportional to
the resources it acts on (and their snapshots), not to the pool, and an idle
satellite no longer lists the whole host.

Not changed: how often the device manager runs, and the per-resource
`zfs list -r` still includes the resource's own snapshots (needed for the
`CF_*` clone bookkeeping). A cache invalidated on the satellite's own `zfs`
commands could reduce the remaining per-run calls further; that is a larger
change, left for a follow-up if wanted.

## Relation to #309

#309 / PR #312 were about other datasets on the same host; v1.20.0 (473795540)
fixed that by listing only the datasets LINSTOR uses. The cost here is the
dataset count inside the LINSTOR pool (and the snapshot recursion), which that
fix does not cover, plus the empty-argument case above, which falls back to a
host-wide listing.

## Tests

- `ZfsUtilsExtCmdTest` (TestExtCmd with canned output), adapted to the new
  commands, plus:
  - `zfsListWithoutDatasetsRunsNoCommand`: no `zfs list` / `zfs get` without a
    dataset argument (the TestExtCmd fails on any unexpected command);
  - `zfsListQueriesPropertiesOnlyForListedDatasets`: the property query runs
    on `rpool/vol0` and `rpool/vol1@s1`, never on the zpool, and the
    `CF_` snapshot still gets `marked_for_deletion`;
  - `zfsListSplitsDatasetsIntoBatchesWithoutAnEmptyOne`: exactly 1000
    datasets give exactly one call.
- `./gradlew :test --tests '*Zfs*'`: 12 tests, 0 failures.
- `./gradlew check` (compile, checkstyle, all modules' tests): passed, 2491 tests, 0 failures.
