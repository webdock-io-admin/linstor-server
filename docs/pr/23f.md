# Fix 23f: no `zfs set snapdev=hidden` after a `zfs clone` that never opened the devices

Base: fix 23e (branch fix/linstor-server-23e-targeted-zfs-list).

## Problem
When a clone finishes, CloneService calls `closeAfterClone()` on the source and the target. For ZFS this ends in `ZfsProvider.closeForClone()`, which runs `zfs set snapdev=hidden` on the zvol. For a 2-volume clone that is 4 commands per storage node (source and clone, per volume), each a ZFS sync task, so a txg wait under load.

For the ZFS_CLONE strategy (`--use-zfs-clone`; `CloneStrategy.ZFS_CLONE(0, false)`, needsOpenDevices=false) `openForClone()` is never called. So snapdev was never made visible, and the clone device path stays null. The four commands change nothing.

The exec sequence of one clone on our dev cluster (2026-11-06) shows exactly these 4 `zfs set snapdev=hidden` per storage node.

## Fix
`ZfsProvider.closeForClone()` hides only if the clone device path is set. `openForClone()` sets it whenever it unhid the snapshot device or created the target. The path is still reset to null either way. No flag.

## Edge (from review)
`snapdev` is inheritable. If a parent dataset has `snapdev=visible`, the old unconditional hide pinned a local `hidden` on each ZFS_CLONE source and target. Now they keep the inherited value. LINSTOR does not set snapdev on parents; the default is hidden.

LVM's closeForClone is unchanged; it has no sync-task cost.
