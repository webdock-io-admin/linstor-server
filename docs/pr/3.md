# satellite: warn if the hostname changed since connecting to the controller

Refs: LINBIT/linstor-server#547

## Problem

A host renamed with `hostnamectl` after `linstor-satellite` started keeps
getting `.res` files with `on "<old-name>"`. `drbdadm adjust` then fails with
`not defined in your config (for this host)`, and so do operations that need
it, such as a diskless make-available for a live migration. Restarting the
satellite fixes it. Nothing in the satellite log points at the rename.

## Cause

The issue report says the satellite caches the hostname at start. That is not
quite right:

- The satellite re-reads `uname -n` on every controller (re)connect:
  `satellite/src/main/java/com/linbit/linstor/api/protobuf/CtrlAuth.java:69`
  (`LinStor.getHostName()`), sent in the auth response.
- The controller stores it as the node property `NodeUname` only then:
  `controller/.../internal/CtrlAuthResponseApiCallHandler.java:119`
  (`updateUnameMap`, set at `:151`).
- The `.res` files render `on` from that stored property:
  `satellite/.../layer/drbd/resfiles/ConfFileBuilder.java:259` (local) and
  `:280` (peers).

So after a rename, `NodeUname` stays stale until the satellite reconnects. A
restart forces that reconnect, which is why it helps.

## Fix

This PR only adds a warning:

- New `satellite/.../core/devmgr/StltUnameChecker.java` compares the live
  hostname (`LinStor.getHostName()`, the same call as `CtrlAuth`) with the
  local node's `NodeUname`. On a new mismatch it logs one warning that names
  both values and says to restart the satellite or reconnect the node. When
  they match again it logs one info line. It doesn't log on every run, and it
  does nothing if either value is missing or empty.
- `DeviceManagerImpl.phaseDispatchDeviceHandlers` calls it once per device
  manager run (`DeviceManagerImpl.java:969`), right after the existing
  `copyReadOnlyData(localNode)`.

Not done here, and why:

- Using the live hostname for the local `on` section: peers would still
  render the old name for this host, and it bypasses the controller's
  duplicate-uname check in `updateUnameMap`.
- Making the satellite reconnect automatically: this disrupts the controller
  connection, and peer `.res` files are only fixed if the controller then
  pushes the new `NodeUname` to the peers.
- Showing the mismatch in the node's status on the controller: this needs a
  new satellite-to-controller notification, which is a larger change. It
  could be a follow-up.

  - one warning after a rename, not repeated on later runs;
